# docs/screen-plan.md 검토 | Codex

검토일: 2026-10-27 · 모델: gpt-5.6-sol · 검토 대상: docs/screen-plan.md v0.1

냉정하게 보면, 현재 문서는 “창작 설정 아카이브” 화면은 비교적 많이 설계했지만 “AI 영상을 실제로 반복 생산하고 게시하는 작업 시스템”의 핵심 데이터가 부족합니다. 특히 프롬프트 자동 조합을 2차로 미루고 백업을 3차로 둔 것은 문서가 선언한 핵심 문제와 정면으로 충돌합니다.

## 1) 정보 구조·데이터 모델의 모순과 누락

### 치명적인 모순

1. 관계 변화의 원본이 두 군데입니다.

- `CharacterRelation.이력`
- `Episode.관계변화[]`

어느 쪽이 원본인지 정의되지 않았습니다. 에피소드에서 관계 변화를 수정하면 관계 이력이 자동으로 바뀌는지, 반대 방향인지, 에피소드를 삭제하면 이력도 사라지는지 알 수 없습니다. 시간이 지나면 반드시 불일치합니다.

권장: 관계 변화는 별도 엔티티로 분리하고 `episodeId`와 `relationId`를 참조하게 해야 합니다.

2. “고정 프롬프트 버전 추적”이 실제로는 불가능합니다.

`Character`에는 프롬프트 버전 숫자만 있고, 과거 프롬프트 본문이나 변경 시점이 없습니다. `Shot`도 최종 조합된 프롬프트의 스냅샷이 아니라 단순 `ko/en` 문자열뿐입니다.

캐릭터 프롬프트를 수정한 뒤 과거 샷을 열면 다음 중 어느 동작인지 정의되지 않았습니다.

- 과거 샷까지 새 프롬프트로 바뀜
- 과거 버전을 유지함
- 사용자에게 갱신 여부를 물음

“사용된 고정 프롬프트 버전 표시”만으로는 재현할 수 없습니다. 버전별 본문 스냅샷이 필요합니다.

3. 소재의 `버전[]`은 모델이 아닙니다.

새 버전이 같은 파일을 대체하는지, 파생 이미지인지, 편집본인지, 썸네일인지 구분할 수 없습니다. AI 생성물에서 중요한 것은 단순 버전 번호보다 다음 관계입니다.

- 어떤 레퍼런스에서 생성되었는가
- 어떤 프롬프트와 모델을 사용했는가
- 어떤 결과물에서 편집·업스케일되었는가
- 어느 샷의 후보·확정본인가

현재 `Asset`에는 이 계보가 없습니다.

4. `Tag`에 서로 다른 개념을 억지로 합쳤습니다.

`습성/소재/역할/관계유형`은 동작과 제약이 다릅니다.

- 역할은 캐릭터에 적용
- 관계 유형은 두 인물 간 관계에 적용
- 습성은 캐릭터와 에피소드에서 재사용
- 소재 태그는 단순 분류

그런데 전부 `Tag`로 취급하면 삭제, 이름 변경, 중복, 적용 대상 검증이 모호해집니다. 역할과 관계 유형은 독립된 설정 엔티티로 두는 편이 맞습니다.

5. 타임라인의 기준이 서로 충돌합니다.

타임라인 축은 “회차 기준”이라고 했지만 다음도 같은 레인에 배치합니다.

- 세계관 조항 변경
- 소재 추가
- 게시·예정
- 기간 필터

소재 추가와 설정 변경은 회차가 없을 수 있습니다. 결국 회차 축과 실제 날짜 축이 혼합됩니다. “회차에 귀속되지 않은 사건”을 어디에 표시할지 정의가 필요합니다.

6. 세계관 미정 항목을 캐릭터 미정 체크리스트에 함께 노출한다는 규칙이 부정확합니다.

프로젝트 전체의 미정 사항과 특정 캐릭터의 미정 사항은 소유 범위가 다릅니다. 한 화면에 모아 보여줄 수는 있지만 데이터까지 같은 배열처럼 취급하면 안 됩니다. 별도 `Decision/OpenIssue` 엔티티가 필요합니다.

### 누락된 화면·상태·흐름

- 생성·수정 화면이 없습니다. “추가 모달”만 언급될 뿐, 긴 배경 서사·프롬프트·레퍼런스를 실제로 어떻게 편집하는지 없습니다.
- 저장 중, 저장 실패, 업로드 실패, 파일 손상, 중복 업로드, 삭제 확인, 복구 상태가 없습니다.
- 보관된 캐릭터·에피소드·소재를 다시 찾고 복원하는 화면이 없습니다.
- 에피소드 복제 시 무엇이 복제되는지 없습니다. 샷, 프롬프트, 게시정보, 확정 클립까지 복제하면 사고가 납니다.
- 회차 순서 변경 시 이미 게시된 URL과 표시 회차가 바뀌는지 정의되지 않았습니다.
- 샷 번호 변경, 샷 삽입·삭제, 샷 복제, 여러 샷 일괄 변경 흐름이 없습니다.
- 한 샷에 여러 생성 후보가 있을 때 비교하고 하나를 확정하는 상태가 없습니다.
- “생성 중” 상태는 외부 생성 도구와 연동하지 않는다면 누가 언제 설정·해제하는지 불명확합니다.
- 생성 실패, 재생성 필요, 후보 검토 중, 확정, 편집 반영, 폐기 같은 실무 상태가 빠졌습니다.
- 게시 완료 후 수정 게시, 삭제, 비공개, 재업로드 상태가 없습니다.
- `Episode.플랫폼[]`, `게시정보[]`, `성과`의 관계가 불명확합니다. 성과는 에피소드 단위가 아니라 플랫폼별 게시물 단위여야 합니다.
- 플랫폼마다 영상 길이·비율·캡션·썸네일이 다른데 `Episode.길이`는 하나뿐입니다.
- 자막 타이밍표가 화면에는 있으나 데이터 모델에 없습니다.
- 편집 메모도 데이터 모델에 없습니다.
- 실제 파일 저장소가 미정인데 업로드·다운로드·버전·썸네일 UI를 확정해 놓았습니다. 저장소 결정 없이는 A-01/A-02를 구체화할 수 없습니다.
- 웹앱과 Notion 중 구현 방식이 미정입니다. 이는 세부 구현 문제가 아니라 버전 관리, 검색, 파일 저장, 관계 데이터, 자동 조합 가능성을 결정하는 선행 결정입니다.

## 2) 실제 AI 영상 제작 워크플로에서 놓친 것

### 레퍼런스 관리

“얼굴 앵커/캐릭터 시트/장소 앵커” 라벨만으로는 부족합니다. 최소한 다음이 필요합니다.

- 사용 가능 여부: 승인 전 / 승인 / 폐기
- 적용 범위: 얼굴, 체형, 의상, 색감, 구도, 장소 구조
- 우선순위뿐 아니라 모델별 첨부 순서와 가중치
- 원본 출처와 사용 권리
- 인물별 대표 앵커의 단일성 또는 유효 기간
- 레퍼런스 간 충돌 메모
- 특정 샷에서 실제 첨부한 파일 스냅샷

현재처럼 캐릭터의 “레퍼런스 우선순위”만 저장하면, 나중에 같은 결과를 재생성할 수 없습니다.

### 프롬프트 조합

문서는 핵심 가치를 “고정 설정과 앵커를 한 번에 모으기”라고 선언하면서 자동 삽입을 2차로 미룹니다. 그러면 MVP에서는 지금처럼 사람이 다음을 다시 복사해야 합니다.

- 캐릭터 고정 프롬프트
- 장소 프롬프트
- 샷 행동·감정·카메라
- 공통 품질 지시
- 금지 요소
- 의상·조명 연속성
- 모델별 문법

즉 핵심 문제가 해결되지 않습니다.

또한 프롬프트는 한/영 두 문자열보다 구성 블록으로 관리해야 합니다.

- 캐릭터 정체성
- 외형·의상
- 장소·시간대
- 행동·감정
- 카메라
- 연속성
- 네거티브 지시
- 출력 규격
- 도구별 추가 인자

“한국어와 영어”보다 “어떤 생성 도구용 프롬프트인가”가 더 중요합니다. 모델마다 지원하는 레퍼런스 방식과 파라미터가 다릅니다.

### 생성 실행과 결과 관리

현재는 샷과 확정 클립 사이 과정이 통째로 없습니다. 실제 작업에서는 한 샷당 2~3개 변형을 만든다고 이미 `content-plan.md`에 명시돼 있습니다. 따라서 최소한 다음 구조가 필요합니다.

`Shot → Generation Run → Variant → Review/Selection → Final Clip`

각 실행에는 다음이 붙어야 합니다.

- 생성 도구·모델·버전
- 실행 시점
- 최종 입력 프롬프트
- 사용 레퍼런스
- 시드·길이·비율·해상도 등 설정
- 결과 파일
- 실패 사유 또는 품질 메모
- 비용 또는 크레딧 사용량
- 선택·폐기 상태

이것이 없으면 “왜 이 샷이 잘 나왔는지”를 학습할 수 없고, 재생성도 불가능합니다.

### 연속성 관리

`content-plan.md`는 같은 날처럼 보이도록 의상·조명을 고정하라고 요구하지만, 화면 기획에는 이를 보장하는 구조가 없습니다.

필요한 것은 캐릭터 기본 의상만이 아니라 에피소드 또는 장면 단위의 연속성 세트입니다.

- 의상
- 헤어·메이크업
- 소품
- 시간대·조명
- 장소 상태
- 인물 위치
- 이전 샷 종료 동작
- 화면 질감 및 색보정 방향

특히 현재 “스마트폰 브이로그 vs 웹드라마”가 미정인데, 이 값은 프로젝트 전체 스타일 프리셋으로 관리해야 합니다.

### 샷 관리

현재 샷 테이블은 콘티의 가장 얕은 정보만 담습니다. 다음이 빠졌습니다.

- 샷 목적과 연결되는 대사·자막
- 앞뒤 샷과의 연결
- 프레임 시작·종료 조건
- 사용 효과음·음악·음성
- 생성 후보 수와 선택 결과
- 편집본에서의 실제 인·아웃 타임
- 재생성 사유
- 합성·보정·업스케일 여부
- 샷별 제작 우선순위 또는 의존성

자막 타이밍표도 샷과 연결돼야 합니다. 별도 텍스트 표로만 두면 샷 순서를 바꿀 때 깨집니다.

### 게시

게시 탭은 기록장 수준입니다. 실제 출고 흐름에는 다음이 필요합니다.

- 플랫폼별 렌더 파일
- 커버/썸네일
- 캡션 버전
- 자막 포함 여부
- 해상도·길이·안전영역 검사
- 저작권·AI 표기 확인
- 승인 또는 게시 전 체크리스트
- 예약 시각과 실제 게시 시각
- 원본 게시물과 재업로드 관계
- 게시 후 수정·삭제·비공개 상태

성과도 수동 숫자 하나가 아니라 플랫폼 게시물별 측정 시점이 있어야 합니다. 오늘 조회수와 일주일 뒤 조회수를 덮어쓰면 추이를 잃습니다.

## 3) 1인 운영자 기준 MVP 범위

### MVP에서 빼야 할 것

- 관계도 캔버스
- 시점 슬라이더
- 타임라인
- 스토리 변화 요약
- 역할·관계 색상 커스터마이징
- 알림
- 멤버·권한
- 업로더 필터
- 캐릭터 카드/리스트 뷰 전환
- 에피소드 칸반/리스트 뷰 전환
- 여러 종류의 대시보드 요약 카드
- 최근 본 항목
- 전체화면 관계도
- 성과 분석
- 접두어를 지원하는 고급 전역 검색
- 한/영 프롬프트를 모든 곳에서 별도로 수동 관리하는 기능
- 내부 마크다운 설정집 편집기
- 광범위한 사용자 정의 태그 시스템

특히 초기 인물이 2명이고 에피소드도 거의 없는 상태에서 관계도·타임라인·대시보드는 보여줄 데이터보다 UI 비용이 큽니다.

홈도 별도 대시보드보다는 “현재 제작 중인 에피소드와 최근 소재”만 보여주는 작업 시작 화면이면 충분합니다.

### MVP에 반드시 들어가야 할 것

1. 프롬프트 조합기

캐릭터·장소·프로젝트 스타일·샷 지시를 합쳐 실제 입력용 프롬프트를 생성하고, 그 결과를 샷에 스냅샷으로 저장해야 합니다. 2차가 아니라 MVP 핵심입니다.

2. 샷별 생성 시도와 후보 관리

샷마다 여러 결과물을 붙이고 비교해 하나를 확정할 수 있어야 합니다. 현재 `확정클립` 하나만 두는 구조로는 실제 작업을 담지 못합니다.

3. 레퍼런스 세트

개별 파일 태그가 아니라 “도윤 얼굴 세트”, “EP.01 의상 세트”, “거실 저녁 세트”처럼 실제 생성 시 함께 첨부할 묶음이 필요합니다.

4. 생성 재현 정보

최종 프롬프트, 사용 모델, 파라미터, 레퍼런스 파일을 생성 시도별로 고정해야 합니다.

5. 연속성 체크

에피소드별 의상·조명·장소·스타일을 한곳에서 고정하고 각 샷이 이를 따르는지 확인할 수 있어야 합니다.

6. 최소 게시 패키지

플랫폼별 최종 파일, 커버, 캡션, 실제 URL, 게시 상태, AI 표기 여부를 관리해야 합니다. 성과 분석은 나중이어도 출고 체크는 MVP에 필요합니다.

7. 백업과 복구

백업을 3차로 미루면 안 됩니다. 최소한 자동 백업 또는 전체 내보내기와 파일 복구 정책은 첫 버전부터 있어야 합니다.

8. 미정 사항 관리

캐릭터 배열에 섞지 말고 프로젝트 전체의 결정 대기 항목을 한 목록에서 관리해야 합니다.

현실적인 1인용 MVP는 다음 정도면 됩니다.

- 프로젝트 스타일·공통 규격
- 캐릭터/장소와 승인된 레퍼런스
- 에피소드/샷
- 프롬프트 조합 및 스냅샷
- 샷별 생성 후보·확정본
- 게시 패키지
- 검색
- 백업

세계관, 관계, 소재는 별도의 거대한 화면보다 위 항목에 연결되는 문서·파일로 시작해도 됩니다.

## 4) 놓친 리스크

### 데이터 유실

- 백업이 3차로 밀려 있습니다.
- 파일 DB와 실제 저장소가 어긋나는 경우가 고려되지 않았습니다.
- 소재 삭제가 이를 사용하는 샷·프롬프트에 미치는 영향이 없습니다.
- 외부 링크만 저장하면 원본 삭제나 권한 만료로 자료가 사라질 수 있습니다.
- 업로드 중 브라우저 종료, 중복 파일, 대용량 영상 업로드 실패, 썸네일 생성 실패가 없습니다.
- JSON 백업이 실제 이미지·영상 파일까지 포함하는지 불명확합니다.

최소한 소프트 삭제, 휴지통, 참조 중인 파일 삭제 금지, 정기 백업, 파일 무결성 검사가 필요합니다.

### 버전 충돌과 재현성

- 캐릭터 프롬프트를 바꾸면 기존 샷이 영향을 받는지 정의되지 않았습니다.
- 장소 프롬프트에는 버전 필드조차 없습니다.
- 현재 모델은 “최신값” 관리에 치우쳐 있고 “당시 사용값” 보존이 없습니다.
- 협업 기능을 추가하면 동시 편집 충돌이 발생하지만 낙관적 잠금, 수정 이력, 병합 정책이 없습니다.
- 외부 생성 서비스의 모델 업데이트로 같은 프롬프트가 다른 결과를 낼 수 있습니다.

모든 생성 실행은 변경 불가능한 입력 스냅샷을 가져야 합니다.

### 소재 저작권·초상권

현재 `Asset`에는 출처와 권리 정보가 전혀 없습니다. 다음이 필요합니다.

- 직접 제작 / AI 생성 / 구매 / 외부 참고 / 제3자 제공
- 원본 URL·제공자
- 라이선스와 상업적 이용 가능 여부
- 인물 초상·퍼블리시티권 동의 여부
- 수정·파생 허용 여부
- 사용 기한과 플랫폼 제한
- 학습·레퍼런스 입력 허용 여부

특히 실사형 남성 얼굴 레퍼런스는 실제 인물 또는 기존 생성물과의 유사성 문제를 따로 관리해야 합니다. “얼굴 앵커”만 표시해서는 법적 검토가 불가능합니다.

### AI 생성물 표기

게시 화면에 AI 생성 여부나 표시 기준이 없습니다. 플랫폼·국가·광고 여부에 따라 표기 요구가 달라질 수 있으므로 다음을 기록해야 합니다.

- 전체 AI 생성 / 일부 합성 / 실제 촬영 기반
- 사용한 생성 도구
- 공개 캡션에 표기했는지
- 플랫폼 자체 AI 라벨을 적용했는지
- 유료 광고·협찬 여부
- 음원·음성도 합성인지

법률 판단을 앱이 자동으로 내릴 필요는 없지만, 게시 전 확인 항목과 증빙은 남겨야 합니다.

### 외부 도구 의존

- 생성 모델·편집 도구·게시 플랫폼이 무엇인지 데이터 모델에 없습니다.
- 서비스 종료, 가격 인상, 크레딧 제한, 모델 교체, 업로드 규격 변경에 대비하지 않았습니다.
- 특정 도구에서만 통하는 프롬프트 문법을 공통 영어 프롬프트로 취급하고 있습니다.
- 플랫폼 API 연동을 고려하면서 토큰 만료, 권한 철회, 게시 실패, 중복 게시를 다루지 않습니다.
- 로컬 폴더 연동은 브라우저 웹앱에서 제약이 크고, 파일 이동·이름 변경 시 참조가 깨질 수 있습니다.
- 클라우드 업로드는 저장 비용, 용량 제한, 다운로드 지연, 개인정보 처리 문제가 생깁니다.

따라서 `Provider/Tool`, `ModelVersion`, `ExternalJob`, `ExternalFileId` 정도는 연동 전부터 데이터 모델에 자리를 마련해야 합니다.

## 우선 바로 고쳐야 할 설계 판단

구현 전에 다음 다섯 가지를 먼저 확정해야 합니다.

1. 웹앱인지 Notion인지  
2. 파일을 어디에 저장하고 어떻게 백업할지  
3. 관계 변화와 설정 변경의 단일 원본이 무엇인지  
4. `Shot → 생성 시도 → 후보 → 확정 클립` 구조  
5. 프롬프트 블록 조합·버전·스냅샷 정책  

이 다섯 가지 없이 현재 화면을 구현하면, 보기 좋은 아카이브는 만들 수 있어도 실제 영상 제작 과정은 다시 채팅·외부 도구·로컬 폴더에서 진행하게 됩니다. 그러면 이 시스템에는 완료된 결과만 사후 입력하게 되고, 가장 먼저 방치되는 운영 도구가 될 가능성이 큽니다.
